# Goal loop

## Sub-features

Empty goal list, loading, populated goal, zero mature denominator, waiting, unreviewed answers, contract gap, draft PR, paused/revoked permission and invalid dates.

## How to get to it (user POV)

Select the project and open Goal loop. The empty page explains the first committed goal. A synced goal shows separate tracking, PR, merge, release, signal and outcome evidence.

## Driving it with the browser

Capture the empty page before sync. Run the local helper, then refresh and verify the displayed mature/qualified/waiting counts match its literal report. No complete rate is shown for zero mature workspaces. Missing external events show unknown coverage, not zero users. Compare the before/after receipts and confirm missing release proof prevents a release-win claim. Pause an active owner policy and confirm its durable revision changed. Revoke it and confirm only a new explicit draft grant is offered. Enter reversed cohort dates and confirm a plain error. Check a narrow viewport for readable controls and no horizontal page overflow. Failure is a count mismatch, a later stage inferred from PR state, a blocked control shown as successful, an uncaught error or clipped content.

## Gotchas

A local protected fake upstream exercises automatic merge gates. Record the real repository branch protection and actual draft/merge/release state separately for each run. A provider deployment receipt is not business-state proof. Release tags in events remain producer claims until matched to provider evidence. A retry must not restart the first-entry clock, including across release labels.

## Existing-repository onboarding

From Goal loop choose Connect repository. Use a private local owner account to connect GitHub, scan the pinned pilot commit, review the real event citation and coverage limits, then propose and adopt a logged-event goal. The owner sees the exact goal and changed source paths before granting a draft-only policy. Readers can inspect saved receipts; delegated keys cannot connect credentials, adopt a goal or grant policy.

Run `scripts/verify_repo_onboarding.py --help` for the local API/CLI proof. The helper requires a loopback preview, private local mail and private provider credential file. It reads a real repo but does not open a PR. Its outcome fixture is synthetic and must be labeled. Scans and preparation are asynchronous: inspect pending, complete, failed and interrupted receipts; retry the same ID/body. Revoke the source or requester before execution and confirm no new provider read occurs.

Capture the running owner page after adoption and after observation. Compare its saved counts, unknown rate and stage labels with the API/CLI receipt. Exact Railway commit proof is required before a release-bound outcome. A merged PR or a matching event tag alone cannot fill the release stage. Inspect a narrow viewport. Failure is a missing source limit, credential exposure, false complete stage, count mismatch or inaccessible control.
