# Governed debug snapshots

A developer opens a trace, lists retained capture metadata, and explicitly selects one snapshot to read. Native workflows support reviewed redacted content; Tracker supports only anonymous catalog-check fixtures. An owner first grants a narrow workflow/environment capture window. Nothing captures prompts, responses, headers or user messages automatically. Tracing and OTLP remain metadata-only.

## Grant, capture, inspect, revoke

1. An owner opens **Traces → Inspect debug capture controls**, selects the capture contract, one code-owned workflow and environment, a capture window, retention and lifetime snapshot budget, then acknowledges the scope. The policy is off until this explicit grant. Every change needs its last-read revision.
2. For native workflows the application explicitly chooses a small JSON payload, reviews it and calls the SDK preparation helper. Tracker instead projects fixed catalog-check fields through a strict allowlist; no question, answer text, feature names, dates, conditions or targeting values are submitted. Common-pattern redaction runs before upload. Flush ordinary metadata first: a snapshot must bind to a retained project/trace/attempt/span in that exact workflow/environment.
3. Send the prepared snapshot to `/v1/debug` with the project's server-side write key and exact approved policy revision. The server applies redaction again, checks scope/budget and encrypts the content before storage. This endpoint is separate from normal event ingestion and its outbox.
4. An editor opens the same frozen trace, lists metadata, then chooses a snapshot. The content read is access-audited and rendered as literal text. Ordinary analytics/audit reads never return this store. Content is untrusted application data, not instructions or independently checked outcome evidence.
5. Capture-window expiry stops new captures. Retained snapshots remain available until their separate TTL. Owner policy change/disable immediately purges previous snapshots. Snapshot expiry rejects reads before hourly physical cleanup. Deleting the source event cascades to its snapshots.

Capture windows are 60 seconds–24 hours. Each snapshot lives 60 seconds–7 days, also bounded by source-event retention. A policy admits at most 100 snapshots, default 20. Its durable admitted count survives snapshot expiry, erasure and cleanup, so a producer cannot reset that budget by waiting. New capacity requires a new owner-reviewed revision. Identical capture retries keep their UUID and do not consume another slot or renew expiry. Changed content at the same UUID conflicts. Identical policy retries do not renew their capture window. Up to 1,000 policy revisions/project are retained as bounded grant history.

## Redaction and encryption limits

Shared Python client/server rules and matching Node rules drop common private-field names and redact recognizable bearer/API credentials, email and phone patterns. Content must be finite JSON, at most five nested levels, 64 fields/object, 100 items/list, 4,000 characters/string and 16 KB before redaction. Unsupported/oversized input is rejected; it is not silently truncated into a favorable-looking answer.

This detector cannot recognize every name, confidential business fact, encoded secret or identifier. Review selected content before preparing it, and inspect newly prepared payloads before upload. Use synthetic values wherever possible. Both policy and producer snapshot require strict `privacy_reviewed: true`; strings/numbers are rejected. The snapshot store is not a raw-prompt archive or general log export. Native snapshots bind to workflow spans, including mapped OTLP spans. Slack snapshots accept only `kind: replay`, `contract: slack-request-v1`, `workflow: slack_read_request` and the typed `catalog-check-replay-v1` envelope. Arbitrary Slack content is rejected before redaction, including fields that a redactor would otherwise remove. Capture binds to a retained terminal quality span on the exact read request/attempt/environment and checks the recorded release. A native capture policy never authorizes Slack capture: an owner must explicitly select the new contract. Old native policy/snapshot retries retain their original semantics.

AES-GCM uses the existing server-only `AFTERSPAN_CONNECTION_KEY` (32 random bytes in URL-safe base64). Enabling capture fails closed if this private-storage key is absent or invalid. Ciphertext binds project, snapshot UUID, policy revision, trace/attempt/span, workflow, environment and content kind; moving a blob to another scope fails authenticated decryption. No plaintext fallback exists. The key loader is shared with existing encrypted provider connections; their format and authenticated context remain unchanged. Key changes require an explicit migration/rotation plan. Encryption does not protect against a fully compromised operator, key access or a decrypted content read; use appropriate infrastructure access and backup retention.

## Anonymous Tracker catalog checks

The fixture stores normalized catalog intent, candidate/source booleans and counts, per-fixture numeric row/version aliases, check results and the exact release. Aliases preserve equality, duplicate rows and ordering without storing original names or source values. At most 50 source rows, 15 claims and 1,000 entries per row can be reconstructed within the existing 16 KB envelope. Unsupported or oversized shapes are omitted with fixed blocked reasons, never silently shortened into runnable evidence.

**Available** means a deterministic check fixture is retained, **not yet replayed**. **Blocked** lists missing request scope, candidate, source, exact release, rejected binding, unsupported source or projection limits. Absent retained capture may mean capture was off, upload was unconfirmed, retention expired, policy changed, or the capture is newer than the frozen receipt. The system does not guess which. Selected reads return the fixture and its limits through UI/API/CLI/MCP; ordinary audit readers never see it. A later capture cannot appear in an earlier frozen receipt.

Tracker captures failed catalog checks only (not uncertain, partial or passing checks) after an owner enables this contract and the producer is configured with that exact policy revision. No policy or producer setting is enabled by this code change. Its uploader flushes metadata first, uses a bounded request, and retries only the same snapshot UUID/body. Business work and model calls are never retried to prove capture. Delivery is best effort.

This is a replay of the **independent catalog check**, not the earlier tool read, parser, model decisions, original wording or Slack exchange. The original request remains unreplayable by design. The Tracker replay helper uses its actual checker, reconstructed anonymous values and the exact recorded code release; a declared release string alone does not prove that checkout was used. The helper cannot grant network or external-action permission. Review fixtures before running them in an isolated read-only environment.

An editor may explicitly copy a selected available fixture into a reviewed regression case. Expected facts start blank and require human review; an observed failed answer never becomes the desired answer automatically. This creates a new curated anonymous case with its own retention, not a durable copy of private debug content or proof of a full historical replay. Saved cases show check availability or missing evidence. Generic historical cases have no established replay availability.

## Access and agent scope

Owners manage capture policy. Editors can inspect policy metadata and selected redacted snapshots. Producers can only submit to an active exact scope using their project write key. Producer keys cannot read or enable policy. Read-purpose keys and ordinary members cannot read content.

Remote MCP requires a separate **`debug:read`** grant and editor membership. It grants neither capture-policy changes nor producer-key access. `debug_capture_policy` reads scope/budget/expiry; `review_debug_snapshots` first lists metadata and accepts an explicit `snapshot_id` for a selected read. Existing analytics, charts, audit, goals and experiment grants do not expand. Role downgrade/removal and grant revocation block subsequent reads. Audit records identify delegated MCP reads separately from account/operator reads. Custom MCP connection support is not a marketplace listing.

## SDK and CLI

Install the [pinned SDK](tracing-sdk.md) first. Python: import `prepare_debug_snapshot` from `afterspan_tracing` and call it with `(span, content, policy_revision, kind='context', privacy_reviewed=True)`. Node: import `prepareDebugSnapshot` from `@afterspan/sdk` and call it with `(span, content, policyRevision, {kind:'context', privacyReviewed:true})`. These helpers only prepare a redacted body; they do not send it, automatically capture content, retry business work or alter normal telemetry. Save the returned body under one stable snapshot UUID for upload retries. After native metadata flush, use an explicitly bounded host/background call to the private endpoint.

```sh
python cli/native_analytics.py debug-policy --project PROJECT
python cli/native_analytics.py debug-policy --project PROJECT --revision 0 --file /private/policy.json
python cli/native_analytics.py debug-capture --file /private/selected-snapshot.json
python cli/native_analytics.py debug-review --project PROJECT --file /private/frozen-trace-query.json
```

Files must be mode 600. `debug-policy` reads with editor authority and changes with owner authority. `debug-capture` uses `NATIVE_ANALYTICS_WRITE_KEY`; the key determines the project, just as normal `send`. The CLI also redacts selected content before HTTP submission. `debug-review` uses editor authority; copy the trace's exact frozen query plus `reference`. First list metadata, then add the selected `snapshot_id`. No raw trace/attempt/span IDs are returned. The producer owns its original span IDs and approved policy revision; these are not obtained by granting a read tool producer-key access.

If metadata has not arrived, capture returns 409. Deliver/retry metadata first, then retry the exact same prepared snapshot; do not rerun business work. Off/expired scope returns 403, stale policy or changed UUID payload 409, exhausted lifetime budget 429, expired retained content 410, and unavailable private storage 503. These are collection limits, not business-operation failures.

Local tests cover default-off behavior, missing encryption configuration, strict review flags, both SDK redactors, immutable retries, scope isolation, exact source bindings, ciphertext authentication, expiry, erasure cascade, durable budget and separate MCP consent/role downgrade. The running local UI listed metadata before a selected read and showed only masked synthetic contact/credential text. The real CLI uploaded, retried and read the selected snapshot; the retry did not consume another slot. This is local synthetic proof. A separate production-service test used the installed Python SDK and an already retained native span in the existing isolated verification project. The policy was initially off with no snapshots. An owner enabled only that synthetic workflow in test for a 60-second capture window, 60-second retention and one-snapshot budget. Pre-upload redaction, metadata-first selected read, strict review flags, exact duplicate expiry/budget behavior and anonymous/producer read denials passed. Disabling the policy purged the snapshot; subsequent reads and stale capture were denied. No real prompt or customer content was uploaded.

The first attempt timed out while observing a duplicate upload; its retry result remained unknown, and a separate policy read confirmed capture disabled with zero retained snapshots. The later bounded test completed all assertions using a privately saved stable snapshot body. Those earlier observations exercised account/API and installed-SDK paths. A later browser-approved production remote MCP client read one installed-SDK-redacted synthetic snapshot: metadata first, then explicit selection. Owner capture was limited to the existing test workflow, 60-second window/retention and one-snapshot budget. The first remote attempts had connection timeouts; cleanup readback confirmed capture off and zero snapshots. A subsequent bounded attempt completed the remote selected read. Disabling capture purged it and denied further remote reads. The temporary OAuth grant was then revoked; its access, MCP initialization and refresh were denied. No real prompt or customer content was uploaded. Independent ciphertext inspection, broader adoption, production capacity and full release clearance remain unproved.
