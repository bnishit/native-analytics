## Choose the deployment before connecting

Ask for the user's Afterspan HTTPS origin only if it is not already known. Never guess an origin or reuse another operator's deployment. Read its `/.well-known/afterspan` and `/healthz`; verify that its declared remote MCP path is `/mcp`. Local HTTP is allowed only on loopback for an explicit local test. Reject credentials, query strings, fragments and extra paths in the origin.

The Codex plugin installs workflows, not a shared remote server. Codex 0.163 does not substitute `${AFTERSPAN_URL}` inside bundled HTTP URLs. Do not edit the installed cache or ask the user to paste keys. Inspect `codex mcp get afterspan --json` first. If absent, register the chosen URL with `codex mcp add afterspan --url https://YOUR_HOST/mcp`. If an existing `afterspan` entry points elsewhere, explain the conflict and get the user's choice before replacing it. The add command may start OAuth itself; inspect the requested scopes in that consent instead of assuming the next login command will narrow them.

For Tracker inspection use `codex mcp login afterspan --scopes audit:read`; for analytics use `analytics:read`. The user signs in, checks the client/callback, chooses a project and approves. Request extra scopes only for the selected task. If add opens a broader consent, select only the permissions needed for this task in Afterspan. The server may narrow the request but cannot add an unrequested permission. Verify the actual granted scopes with connection_status. Reconnect/restart the client after configuration or scope changes so its running MCP connection reloads. Then call connection_status and verify the actual project/scopes before doing work. Existing tokens do not gain permissions because the guide asks for them. View/revoke connections at `/assets/mcp-connect.html`.

For Tracker call get_workflow(name="improve-tracker"). A missing experiment grant must give one concrete scoped login command, not an operator-token workaround. Full case/release/follow-up work needs `audit:read,experiments:write,releases:write,followups:write`; add `debug:read` only for a selected retained debug fixture. Goal creation needs its own separate `goals:write`. An owner still adopts release evidence; GitHub/deploy access remains on the coding host.

Call connection_status and confirm the project. For a Tracker failure, load get_workflow(name="improve-tracker") and follow its scoped evidence path; audit-only access cannot browse aggregate catalogs. For an analytics task, load get_workflow(name="build-dashboard"), call event_catalog with a bounded window, then setup_status. Use query_metric for aggregate reads and return its native view_url; do not substitute a standalone report or owner-token raw export for a missing connection. Distinguish configured collection from observed application activity. If authorized, exercise one safe real application interaction, then query_metric for its expected event. Do not manufacture production events to claim a working integration. Name test traffic separately, and do not claim that unrelated historical events prove the new interaction. If the event cannot be isolated, report that limit.

Finish with the project, scopes, collection evidence, time window and one supported next step. This connection cannot deploy, issue producer keys or administer accounts. Existing local CLI setup remains available for those separately authorized workflows.
